# Initial Technical Design

## 1. Architecture goals

- Run locally with a simple installation and no required account.
- Preserve a clean boundary between user interface, learning logic, content sources, and ML providers.
- Support a later phone client without rewriting core domain rules.
- Work offline for ordinary deck management and study after content/audio is cached.
- Keep user data portable and inspectable.

## 2. Proposed architecture

Use a local web application with a typed API and a local database:

```text
Desktop browser / installable PWA
              |
        Local HTTP API
   +----------+-----------+
   |          |           |
Study      Content      Evaluation
engine     service      service
   |          |           |
   +------ SQLite --------+
              |
   Provider adapters (dictionary, TTS, STT, embeddings, LLM)
```

Recommended starting stack:

- **Frontend:** React + TypeScript, responsive and installable as a PWA.
- **Backend:** Python + FastAPI, well suited to text/audio/ML integrations.
- **Database:** SQLite with migrations; repository interfaces keep a future hosted database possible.
- **Local media:** content-addressed files for cached audio and images, referenced from the database.
- **API contract:** OpenAPI generated by FastAPI; generate a typed frontend client.

The backend owns study scheduling and scoring so later desktop and mobile clients behave consistently.

## 3. Core modules

### Content

Owns language items, senses, forms, audio, images, tags, decks, membership, sources, and imports. It resolves partial entry through pluggable dictionary/search providers.

### Study

Builds a reproducible session from deck selection, filters, requested count, study mode, and a recorded selection policy/version. It schedules future reviews from attempt evidence.

### Evaluation

Normalizes answers and dispatches to character, pinyin, meaning, or speech evaluators. All evaluators return a shared result shape:

```json
{
  "score": 0.86,
  "verdict": "mostly_correct",
  "confidence": 0.91,
  "dimensions": {"meaning": 0.95, "tone": 0.62},
  "feedback": [],
  "evaluatorVersion": "..."
}
```

### Mastery

Maintains skill-specific estimates and review schedules from immutable attempts. Derived mastery can be rebuilt when algorithms change.

### Intelligence

Coordinates retrieval, embeddings, generation, validation, and ranking. Provider interfaces prevent the product from depending on one model vendor. Every suggestion stores provenance, model/provider version, prompt-policy version, and validation results.

## 4. Study session selection

The first selector should be deterministic for a given snapshot and seed:

1. Apply deck and user filters.
2. Determine eligible item-skill pairs for the chosen study mode.
3. Score by due state, weakness, error streak, latency, novelty, and user focus.
4. Enforce configurable new/review balance and diversity constraints.
5. Select exactly the requested count where enough eligible items exist.
6. Save the candidate inputs, selection reasons, algorithm version, and random seed.

This makes sessions explainable and bugs reproducible. ML ranking can later become an additional signal rather than replacing the baseline.

## 5. Evaluation pipeline

1. Preserve the raw learner response.
2. Normalize into an evaluation-only form without altering stored input.
3. Run format-specific checks.
4. Use semantic or speech models only when simpler checks are insufficient.
5. Return dimensional scores, feedback, and confidence.
6. Ask for self-assessment when confidence falls below a threshold.
7. Record any learner override separately.
8. Update derived mastery and scheduling.

## 6. Local-first and mobile path

For the MVP, the API binds only to the local machine and SQLite is the source of truth. Export creates a versioned archive of database content and media.

For mobile, keep the same API/domain contracts while introducing:

- a hosted sync service and authentication;
- per-record IDs generated client-side;
- append-only attempts for easy reconciliation;
- explicit timestamps and schema versions;
- conflict policies for editable cards and deck membership;
- cached study sessions for offline use.

The initial frontend can later be wrapped or replaced by a native client without changing learning semantics.

## 7. Privacy and safety

- Store learning history and recordings locally by default.
- Require explicit opt-in before sending text or audio to cloud ML services.
- Indicate which provider will receive data before enabling it.
- Allow recordings and history to be deleted or exported.
- Never execute generated content or treat model output as trusted markup.
- Preserve licenses and attribution for dictionary and corpus content.

## 8. Testing strategy

- Unit tests for Chinese/pinyin normalization and evaluator boundaries.
- Property tests for session-size and eligibility invariants.
- Golden test cases for English semantic and pinyin/tone judgments.
- Scheduler simulations to detect starvation or excessive repetition.
- Contract tests for ML/dictionary provider adapters.
- End-to-end tests for deck creation, session configuration, interruption/resume, and export.
- Human review sets for sentence naturalness and proficiency level.

## 9. Delivery phases

### Phase 1: Non-ML learning loop

Language items, decks, configurable typed study modes, session sizing, attempts, mastery, and local persistence.

### Phase 2: Assisted content entry

Dictionary search, pinyin normalization, duplicate detection, audio generation/cache, and import/export.

### Phase 3: Context and semantic evaluation

Phrase/sentence retrieval and generation with review, English semantic scoring, and improved adaptive selection.

### Phase 4: Speech and mobile readiness

Speech input, pronunciation feedback, offline packaging, sync contracts, and a mobile prototype.

## 10. Confirmed implementation choices

- Use React and TypeScript for the frontend.
- Use Python and FastAPI for the backend.
- Use SQLite as the local system of record.
- Display simplified Chinese by default while preserving traditional forms.
- Implement dictionary-assisted entry before generated content.

## 11. Decisions still required

- Select redistributable dictionary and example sources.
- Choose initial local or cloud text-to-speech and speech-to-text providers.
- Define a calibrated evaluation test set for the first five study modes.
